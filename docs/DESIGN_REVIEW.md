复核日期：2026-09-29。依据为当前工作区文件的静态阅读，没有运行游戏；工作区已有用户修改，本次不修改游戏代码。

## 旧稿如何保留

完整原稿见 [历史草案](archive/GAME_DESIGN_2026-09-29_DRAFT.md)。其中“已确认”是旧文档的记录，不意味着本次重新逐条获得确认。新补充的规则属于实施基线，不伪装成此前用户的决定。

## 需要解决的设计问题

| 旧稿问题 | 对开发的影响 | 处理原则 |
| --- | --- | --- |
| 已确认表与“首版未确认”重复且矛盾 | 开发者不知道哪个版本有效 | 当前规则只在主策划定义；历史稿不再指导实现 |
| 最终任务从独立关卡增加到 5 关、40 房 | 制作与测试规模显著增长 | 单独决定首版范围，不把长流程误当成必需玩法 |
| 最终解锁永久保留，同时失败又必须重打普通三关 | 解锁状态与进入资格混在一起 | 必须明确可否直接重试、何时消耗资格 |
| 九种房间规格、分支、环路、同关不重复一起加入 | 随机生成和资产数量成为前置风险 | 地图结构、房间模板与战斗配置分离；先验证可达性 |
| 手枪备弹有限但没有保底 | 出现无法清房、无法拿到补给的死局 | 明确无弹时仍可继续战斗的机制 |
| 只有武器和敌人数值，没有产出与价格 | 商店、永久强化、通关速度无法验证 | 明确保底收益、消费次数、升级总成本和样例账本 |
| 10–15 分钟是目标，却没有测量口径 | 容易靠增加房间和血量拖时间 | 区分估算和试玩结果；完成优先于时长 |
| 道具和支援只是名称 | 每个名称隐藏独立的交互和状态逻辑 | 首版保留项必须写出使用条件、命中、持续时间、上限 |
| 无失败、退出、存档损坏规则 | 易重复结算或丢失永久进度 | 结算幂等，写入备份，明确不支持局内续玩时的行为 |

## 复用方法

不重建项目、不替换素材包、不先写通用框架。先修生命与子弹职责，提取一个 Player 场景，让测试场和正式入口使用同一玩家；再逐项接武器、房间、结算与存档。新系统保持小而明确，数值集中配置。

不要为了延长通关时间先增加房间、敌人数、武器或局外养成。只有当前里程碑验收通过，才进入下一个里程碑。
